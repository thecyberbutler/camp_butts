# Email-only account identity

Owner request, 2026-11-25: no user accounts have usernames. Each campground uses a unique,
case-insensitive email for local sign-in, signup and protected operator lookup. Internal UUIDs
remain stable. The same email may independently register at different campgrounds; Google
links remain provider-subject links and are never merged or authenticated by matching email.

The custom AbstractUser model removes its username field and uses an email-first manager.
Allauth uses its supported email-only/no-username settings. Forms/manager/Google normalize
email; PostgreSQL retains the existing lowercase email uniqueness constraint and additionally
rejects empty email. Login, duplicate-signup responses, Axes email/IP limits, Argon2id, account
approval, recent reauthentication, MFA, session ceilings and tenant boundaries remain enforced.
Staff lists/audit actors/operator commands now identify accounts by email; no public camper
email directory is introduced. Third-party Axes APIs still call their identifier field
`username`; it contains the normalized email, not a user-selectable account handle.

## Migration and deployment requirements

`accounts.0003_email_identity` validates all stored account emails before altering state.
Invalid, oversized, normalization-colliding, secondary or mismatched email-address records
stop migration with a generic diagnostic. Resolve them through independent owner/operator
review; do not invent an email, silently merge accounts or mark addresses verified.

The migration retains UUIDs, password hashes, Google links, roles, MFA, reservations and
email-verification state. It normalizes email, increments security versions, and deletes
server-side sessions (including pending OAuth/MFA/signup state). Recent legacy login-failure
counts are carried into the email identity without deleting original IP/attempt history.
Their existing 15-minute cooldown conservatively restarts; users with recent failed attempts
may need to wait up to 15 minutes. No rate limit or lockout is reset to permit sign-in.

Historical migrations remain unchanged. Removing stored usernames is intentionally
irreversible; no autogenerated surrogate or unsafe data recreation is supplied. Stop web and
jobs, create/verify an encrypted backup, check every tenant's migration prerequisites and
run the tenant migration under the migration identity. Reapply normal reviewed protections/
grants and deployment checks. Do not roll back to a username-based image on the new schema.
Recovery requires a separately reviewed forward fix or isolated restore; never restore stale
sessions/privileges directly over live data. Disclose the exact transcript before deployment.
